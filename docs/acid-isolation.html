Transactions and consistency交易與一致性

ACID and isolationACID 與隔離等級

A transaction makes a group of changes behave like one. How much it protects you from other transactions is a separate dial. 交易讓一組修改表現得像一個動作。至於它能幫你擋住其他交易到什麼程度，那是另一顆旋鈕。

Four promises四個承諾

"Consistency" is mostly your job: the database only enforces the rules you declared as constraints. 「一致性」大部分是你的責任：資料庫只會強制你宣告成 constraint 的規則。

The isolation dial隔離等級這顆旋鈕

The same name doesn't mean the same behavior: MySQL's and PostgreSQL's REPEATABLE READ handle concurrent updates differently. See MVCC: MySQL vs PostgreSQL. 名字一樣，行為不一定一樣：MySQL 和 PostgreSQL 的 REPEATABLE READ 處理並行更新的方式不同。請看 MVCC：MySQL 與 PostgreSQL。

A transaction is not a lock交易不等於鎖

Both run at once. Nothing waits unless a statement takes a lock, a version check fails, or a constraint says no. That is the whole story of lost updates. 兩者會同時執行。除非某個 SQL 拿了鎖、版本檢查失敗，或 constraint 拒絕，否則誰也不會等誰。lost update 就是這樣發生的。

What to remember記住這些

Know the level actually in effect (MySQL: REPEATABLE READ, PostgreSQL: READ COMMITTED, unless you changed it). For every write path, name the anomaly it risks and the guard that stops it. 先確認實際生效的隔離等級（沒改過的話：MySQL 是 REPEATABLE READ，PostgreSQL 是 READ COMMITTED）。每一條寫入路徑，都要說得出它可能出現哪種異常，以及用什麼方式擋住。
