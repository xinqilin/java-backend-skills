MVCC: MySQL vs PostgreSQLMVCC：MySQL 與 PostgreSQL

Both databases keep old versions of rows so readers don't block writers. They keep them in different places, and they react differently when two writers collide. 兩個資料庫都會保留資料列的舊版本，讓讀的人不會擋到寫的人。但舊版本放的位置不同，兩個人同時寫的時候，反應也不同。

Why it matters for your code這對你的程式碼有什麼影響

The usual JPA shape (load an entity, change it, let Hibernate flush) mixes a snapshot read with a write to the newest version. The MySQL manual itself warns against mixing those two in one REPEATABLE READ transaction. 常見的 JPA 寫法（讀出 entity、修改它、讓 Hibernate flush）會把 snapshot 讀取和「寫到最新版本」混在一起。MySQL 手冊本身就建議不要在同一個 REPEATABLE READ 交易裡這樣混用。

In PostgreSQL, long-running transactions keep old versions alive, so tables bloat until VACUUM can clean them. 在 PostgreSQL，跑很久的交易會讓舊版本一直留著，表格會一直膨脹，直到 VACUUM 能把它們清掉為止。

Write code that is safe on both寫出在兩邊都安全的程式碼

Use guards that don't depend on the isolation level: an atomic conditional UPDATE, a @Version column, an explicit lock, or a constraint. Keep transactions short. 使用不依賴隔離等級的防護：一條包含條件的 UPDATE、@Version 欄位、明確加鎖，或 constraint。交易盡量短。
