Outbox and idempotencyOutbox 與冪等性

Saving an order and telling other systems about it are two different places. If they can disagree, eventually they will. 存訂單和通知其他系統是兩個不同的地方。只要它們有可能不一致，總有一天會不一致。

The dual write雙寫問題

Publishing first is no better: if the transaction then rolls back, consumers act on an order that never existed. 先發送也沒比較好：如果交易接著 rollback，下游會處理一筆根本不存在的訂單。

The outbox: one transaction, then a relayOutbox：一個交易，再交給轉送程式

Either both rows commit or neither does. The relay may publish the same event twice (it can crash after sending and before marking it sent), so consumers must ignore duplicates by event id. 兩筆資料要嘛一起 commit，要嘛都沒有。轉送程式可能把同一個事件送兩次（送出後、標記已送前當機），所以下游要依事件 id 忽略重複的事件。

Idempotency keys: retries do it onceIdempotency key：重試只會生效一次

Store the key under a unique constraint in the same transaction as the payment. Two concurrent duplicates can't both insert it. 把 key 和付款放在同一個交易裡存，並加上 unique constraint。兩個同時到達的重複請求，不可能都存得進去。
