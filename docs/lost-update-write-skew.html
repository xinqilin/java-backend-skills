Transactions and consistency交易與一致性

Lost update and write skewLost update 與 write skew

Two requests arrive at the same time. Each one is correct alone. Together, they break your data, even inside @Transactional. 兩個請求同時到達。各自單獨跑都沒問題，一起跑就把資料弄壞了，即使包在 @Transactional 裡也一樣。

Lost update: two withdrawals of 10Lost update：同時提款兩次，各 10 元

Each request loads the account, subtracts in Java, and saves. The second save overwrites the first one. 兩個請求都是讀出帳戶、在 Java 裡相減、再存回去。第二次存檔把第一次蓋掉了。

What each database does at step 4第 4 步，各資料庫怎麼處理

"REPEATABLE READ prevents lost updates" is only true for PostgreSQL. In MySQL, the UPDATE applies to the newest row and no error is raised. 「REPEATABLE READ 能防止 lost update」只對 PostgreSQL 成立。在 MySQL，UPDATE 會直接套用在最新的那一筆上，不會報錯。

The fix: let the database check解法：讓資料庫來檢查

@Modifying
@Query("update Account a set a.balance = a.balance - :amt " +
       "where a.id = :id and a.balance >= :amt")
int withdraw(@Param("id") long id, @Param("amt") BigDecimal amt); // 0 rows = rejected

One statement reads and writes, so nothing can sneak in between. Other options: a @Version column (the loser gets an error and retries), or SELECT … FOR UPDATE (the second request waits). 讀和寫在同一個 SQL 完成，中間沒有空隙可以插隊。其他做法：加 @Version 欄位（後到的會收到錯誤並重試），或用 SELECT … FOR UPDATE（第二個請求會排隊等待）。

Write skew: the last doctor on callWrite skew：最後一位值班醫生

PostgreSQL REPEATABLE READ allows this. SERIALIZABLE stops it (one transaction fails with 40001 and retries). Locking the rows you checked (FOR UPDATE) also works. If the conflicting row doesn't exist yet, such as a double booking, use a constraint. PostgreSQL 的 REPEATABLE READ 擋不住這種情況。SERIALIZABLE 擋得住（其中一筆會以 40001 失敗，重試即可）。把檢查過的資料列鎖起來（FOR UPDATE）也行。如果會衝突的那一列根本還不存在（例如重複訂位），就要用 constraint。
